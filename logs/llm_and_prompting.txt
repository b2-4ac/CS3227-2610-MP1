SUMMARY OF LLM PROMPTS AND DEVELOPMENT WORKFLOW

The LLM was used throughout the development of the Study Session Tracker as a supporting tool for planning, implementation, debugging, testing, and architectural decision-making. Rather than using a single prompt to generate the complete application, the interaction followed an iterative workflow in which individual components and problems were discussed as they arose. Prompts generally began with broader questions about implementation or design and became increasingly specific as the project developed.

At the beginning of the project, the prompts focused primarily on planning and software architecture. Questions were asked about suitable desktop application ideas and how the Model-View-Controller (MVC) architecture could be applied to a Study Session Tracker. These discussions were used to establish the initial separation between models, controllers, application logic, persistence, and the user interface. The LLM was therefore initially used more as a design and explanation tool than as a direct code-generation tool.

Once the general architecture had been established, the prompts became more implementation-focused. Individual classes such as StudySession, Subject, StudyTimer, TimerController, StudySessionRepository, and ConsoleUI were discussed separately. Instead of requesting the entire application at once, prompts focused on the responsibility and implementation of one component at a time. Follow-up questions were frequently used to understand why a particular class or design decision was necessary. For example, the distinction between StudyTimer and TimerController was discussed to clarify why timer calculations and application-level coordination should remain separate.

The prompting process was iterative. Suggestions from one response frequently led to new requirements or exposed issues that required additional prompts. The implementation of pause and resume functionality is an example of this. The original timer design could determine elapsed time using the start and end timestamps. Once pausing was introduced, this was no longer sufficient because paused time should not contribute to the recorded study duration. Subsequent prompts therefore explored how to accumulate active study intervals separately while still retaining the overall start and end times of a session.

A similar iterative process occurred with the command-line interface. Initial prompts dealt with displaying basic options for starting and stopping a session. As the timer gained additional states, the prompts became more precise and described the expected menu behaviour for each state. When the timer had not started, the menu should allow a session to be started. When running, the available actions should include pausing and stopping. When paused, the actions should instead include resuming and stopping. This discussion also led to reconsideration of the use of Boolean variables in ConsoleUI. The LLM suggested using the existing TimerState enumeration as the single source of truth rather than independently maintaining isTimerRunning and isTimerPaused values in the user interface.

Prompts were also used to learn unfamiliar libraries and development tools rather than simply requesting finished code. Questions about Jackson explored how Java objects could be serialized to JSON, why JavaTimeModule was necessary for classes such as LocalDateTime and Duration, and how JsonCreator and JsonProperty could be used during deserialization. This allowed the generated code to be considered alongside explanations of why particular APIs and annotations were required.

The same approach was used for Gradle. Prompts covered configuring the project for Java 25, generating and using the Gradle wrapper, locating compiled output, skipping tests when necessary, and configuring the Shadow plugin for executable JAR creation. These interactions demonstrated the importance of supplying exact environmental information when asking technical questions. In particular, an initially suggested Shadow plugin version was incompatible with Gradle 9.1.0 and resulted in an AdhocComponentWithVariants-related error. The error was returned to the LLM in a subsequent prompt, and the problem was narrowed to plugin compatibility. A compatible Shadow version was then selected. This demonstrated that LLM responses still needed to be tested against the actual development environment rather than assumed to be correct.

Testing was another area in which prompts were used as both an implementation and learning aid. Questions were asked about creating JUnit tests for StudySession constructor validation, appropriate assertions, package placement, and imports. The generated tests provided a starting point, but their usefulness depended on running them against the actual implementation. This reinforced a workflow in which generated code was followed by compilation and execution rather than being accepted without verification.

As development progressed, prompts increasingly involved debugging existing code rather than generating new components. In these cases, the prompt generally included the behaviour that had changed or the error that had appeared. For example, after moving sessions.json to /data/sessions.json, the application stopped creating its storage file. The prompt described the exact change that preceded the failure. The LLM identified that the leading slash caused the path to be interpreted differently and also identified that the parent data directory needed to exist before the JSON file could be written. The proposed solution was then incorporated and tested in the application.

This debugging workflow highlighted an important pattern in the interactions. Prompts containing concrete information such as source code, error messages, version numbers, and the expected result generally produced more useful answers than broad descriptions of a problem. When an initial suggestion did not work, the next prompt included the resulting error or additional implementation details. As a result, prompting became progressively more constrained until the cause of the problem could be identified.

The project's requirements also evolved through prompting. Initially, subjects were entered manually whenever a study session was started. A later prompt introduced the requirement for users to maintain a fixed set of subjects that could be added to or deleted. The discussion then expanded into multiple related implementation tasks: creating subject persistence, introducing a SubjectRepository and SubjectController, preventing duplicate subjects, adding subject-management options to the command-line interface, and selecting a stored subject when starting a session. This demonstrates how a high-level feature request was progressively decomposed into smaller implementation prompts.

The same pattern was followed when statistics were introduced. The initial prompt described the desired user-facing functionality: users should be able to specify a period of dates and view how much time they had spent studying, including the subjects studied during that period. The response decomposed the requirement into filtering StudySession objects by date, accumulating Duration values, grouping durations according to subject, validating date input, and displaying the results. A StatisticsService was proposed to keep these calculations outside the user interface. Further discussion also identified how the design could later be extended with additional statistics.

Throughout the project, the LLM was therefore used in several different roles. It provided explanations of unfamiliar concepts, proposed initial implementations, reviewed architectural choices, suggested refactorings, generated test cases, and assisted with debugging. The type of prompt used depended on the stage of development. Early prompts tended to ask what should be built and how components should be organised, while later prompts increasingly supplied existing code and asked how it could be modified or why it was behaving incorrectly.

The workflow generally followed the sequence of asking a focused question, reviewing the suggested explanation or implementation, integrating the relevant parts manually, compiling or running the application, and returning with a more specific follow-up prompt when a problem was discovered. Consequently, the LLM did not directly produce the final application in a single generation. The implementation emerged through repeated cycles of prompting, manual integration, testing, debugging, and refinement.

The interactions also demonstrated limitations of LLM-assisted development. Generated answers sometimes depended on assumptions about the current implementation or development environment. These assumptions were not always correct, as demonstrated by the Shadow plugin compatibility issue. Code suggestions also needed to be adapted to match existing class names, methods, fields, and architectural decisions. In several cases, manually inspecting the code or executing the application was more effective for determining whether a proposed solution actually worked.

As the project progressed, the prompts generally became more effective because more contextual information was included. Instead of asking broad questions such as how a feature should be implemented, later prompts often supplied the current implementation and explicitly described the required behaviour. Providing exact version numbers, error messages, relevant source code, and constraints reduced the number of assumptions the LLM had to make.

Overall, the LLM was used as an iterative development assistant rather than as a replacement for the development process. Prompting was most useful for generating possible approaches, explaining concepts, identifying likely causes of errors, and suggesting improvements to the application's structure. Manual engineering work remained necessary to determine whether suggestions were appropriate, integrate them with the existing codebase, compile and test the results, and make final architectural decisions. The prompting workflow therefore complemented traditional software development practices of implementation, testing, debugging, and refinement rather than replacing them.
